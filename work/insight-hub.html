W-07Palantir Foundry · Case study · In review

EHS Insight Hub

I designed and built a Palantir Foundry widget that puts EHS cases, events, concerns and insights into one ontology of 12 object types, computes KPIs and status in a single logic layer, and presents them in a layout EHS users already know from Gensuite.

  3. Status

  4. Why it matters

Step 1 · Problem

The situation

EHS work produces several kinds of record that belong together. An event happens at a site. A case is opened to manage it. Concerns are raised along the way, some of them before anything goes wrong. Over time, patterns across all of these become insights that leadership should act on. In most EHS systems these sit in separate modules and separate exports, so seeing one site's picture means joining them by hand.

That join is where numbers drift. When each report applies its own filter for what counts as open, overdue or closed, two dashboards can show two different figures for the same site in the same week. The Gensuite refresh attacked the same problem at the point of capture. Hexion's move to Palantir Foundry gave me the chance to fix it in the data model rather than in each report.

Step 2 · Constraints

Constraints

  • The people using it already work in Gensuite every day. A new tool that asked them to learn a new layout would compete with the system of record instead of supporting it.
  • KPIs and status labels feed management reporting, so they had to be computed the same way everywhere, from rules that a reviewer can read.
  • The ontology is shared with the wider Foundry migration, so changes go through a branch and a reviewed proposal before reaching main. Nothing ships by editing production directly.
  • EHS records are sensitive. Nothing from the tenant appears on this page: the view below is a mock-up with invented values.
Step 3 · What I did

What I built

The work has three layers. The ontology gives every EHS record a typed object with links to the records it relates to, so a case knows its events and an insight knows the concerns behind it. A single logic module computes every KPI and decides every status label from those objects. The widget only displays what the logic returns, so no screen carries a rule of its own.

Step 4 · Decisions

Decisions I made and why

  • I put every KPI and status rule in one logic module instead of inside each view. When the definition of overdue changes, it changes once, and every tile and list agrees.
  • I modelled insights as objects in the ontology, not as text in a report. That way an insight keeps its links to the concerns and events behind it, and anyone can trace the claim back to the records.
  • I copied the Gensuite layout on purpose. Familiarity was worth more than novelty for people who spend their day in the system of record.
  • I built on a branch and sent it through a merge proposal, the same review path as the rest of the Foundry migration, rather than editing the shared ontology directly.
Step 5 · Status

Where it stands

The ontology and widget are built and verified on a Foundry branch. On that branch, the 12 object types index 190 cases, 1,221 events, 11,546 concerns and 82 insights. The merge proposal that brings it to main is in review. I will update this page when it merges.

What it means for a leader

When a safety KPI reaches a review meeting, someone should be able to ask where it came from and get an answer in one click. Here each number comes from one rule in code, applied to typed records that link back to the events and concerns behind them.
